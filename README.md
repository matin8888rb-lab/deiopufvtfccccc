# COUNCIL HQ | مرکز فرماندهی شورا

پنل فارسی، راست‌چین و سازگار با موبایل برای مدیریت یک شورای چندنقشی. رابط در GitHub Pages اجرا می‌شود و بخش‌های عملیاتی پس از ورود، داده‌ها را با Supabase همگام می‌کنند.

## بخش‌های آماده
- داشبورد مرکزی و وضعیت پروژه‌ها
- اتاق شورا با نمونه گفت‌وگو و امکان ثبت پیام کاربر
- هفت پروفایل با نقش و رنگ ثابت
- مدیریت پروژه‌ها و ثبت پروژه جدید
- مرکز وظایف ابری: مسئول، اولویت، موعد، وضعیت و وابستگی بین وظایف
- اتاق جلسات: شرکت‌کنندگان، شروع/پایان و ثبت صورت‌جلسه
- دفتر تصمیم‌ها: وضعیت تصمیم، میزان اطمینان، نظر قاضی، مخالفت مستدل و شواهد
- تاریخچه رویدادهای عملیاتی در audit_events
- دفترچه شورا و ثبت یادداشت
- آزمایشگاه و ثبت پیشنهاد پژوهش
- اعلان‌ها و تنظیمات
- ذخیره محلی پشتیبان و همگام‌سازی ابری پروژه‌ها، دفترچه، پیشنهادهای پژوهشی و پیام‌های کاربر با Supabase
- پشتیبان‌گیری و بازیابی JSON
- PWA و cache آفلاین پایه
- ثبت‌نام و ورود ایمیل/رمز عبور با Supabase Auth
- کنترل‌های یکپارچگی سمت پایگاه داده برای جلوگیری از اتصال وظایف، اعضا، جلسات و شواهد بین فضاهای کاری متفاوت
- ایجاد خودکار فضای کاری خصوصی و هفت پروفایل شورا پس از اولین ورود
- جداسازی داده‌های هر حساب با workspace خصوصی و RLS؛ ذخیره محلی به‌عنوان پشتیبان

## انتشار
برای فعال‌سازی اولیه، یک‌بار وارد **Settings → Pages** مخزن شو و در بخش Build and deployment، گزینه **GitHub Actions** را به‌عنوان Source انتخاب کن. سپس Workflow موجود در `.github/workflows/deploy-pages.yml` پس از هر push به شاخه `main` سایت را منتشر می‌کند. توکن اتصال فعلی اجازه فعال‌سازی Pages از طریق API را ندارد، بنابراین این تنظیم اولیه باید توسط مالک مخزن انجام شود.

## راه‌اندازی احراز هویت Supabase
پروژه به Supabase متصل است. برای فعال شدن تأیید ایمیل در GitHub Pages:
1. در Supabase Dashboard، وارد Authentication → URL Configuration شو.
2. مقدار Site URL را روی آدرس GitHub Pages همین مخزن قرار بده: `https://matin8888rb-lab.github.io/deiopufvtfccccc/`.
3. همین آدرس را در Redirect URLs نیز مجاز کن.
4. سپس در سایت، حساب بساز و ایمیل تأیید را باز کن.

کلید داخل کد فقط Publishable Key است و برای استفاده در مرورگر طراحی شده؛ هرگز Secret یا service_role key را در GitHub قرار نده.

## محدودیت‌های مهم و شفاف
این نسخه هنوز یک سامانه چندعاملی واقعی نیست:
- پیام‌های اعضا در اتاق شورا داده‌های نمونه‌اند؛ پاسخ هوشمند تولید نمی‌شود.
- احراز هویت، فضای کاری، هفت پروفایل، پروژه‌ها، وظایف، وابستگی‌ها، جلسات، شرکت‌کنندگان، تصمیم‌ها، شواهد، رویدادهای ممیزی، دفترچه، پیشنهادهای پژوهشی و پیام‌های ارسالی کاربر در Supabase ذخیره و هنگام ورود بازیابی می‌شوند. LocalStorage نسخه پشتیبان دستگاه است. حذف همگام‌شده برای پروژه‌ها/دفترچه/پژوهش/پیام‌ها و مدیریت تعارض چنددستگاهی هنوز پیاده‌سازی نشده است.
- Service Worker فقط cache آفلاین پایه فراهم می‌کند و به معنی اجرای دائمی در پس‌زمینه نیست.
- وظایف عملیاتی کاربر و جلسات شورا فعال‌اند؛ صف خودکار عامل‌ها، پژوهش وب، زمان‌بندی مستقل و اجرای خودکار هنوز فعال نیستند.

## نقشه اتصال backend
جزئیات معماری امن و مراحل فعال‌سازی در [docs/BACKEND_INTEGRATION.md](docs/BACKEND_INTEGRATION.md) ثبت شده است. تست‌های منطق مستقل با دستور `node --test tests/council-ops.test.mjs` اجرا می‌شوند.

## زیرساخت لازم برای نسخه عملیاتی کامل
برای فعال شدن قابلیت‌های واقعی باید یک backend امن به پروژه متصل شود:
1. احراز هویت و پایگاه داده با دسترسی مبتنی بر مالکیت و Row Level Security.
2. API سمت سرور برای مدل زبانی؛ کلیدهای محرمانه هرگز نباید در فایل‌های عمومی یا مرورگر قرار بگیرند.
3. موتور گردش‌کار چندعاملی، صف وظایف و زمان‌بند سمت سرور.
4. ثبت ممیزی، سقف مصرف، توقف اضطراری و تأیید انسانی برای اقدامات حساس.
5. اتصال جست‌وجوی منابع و ذخیره شواهد برای پژوهش‌ها.

هیچ کلید محرمانه یا service_role در مخزن قرار نگرفته است. اتصال Supabase برای Auth و داده‌های اولیه فضای کاری برقرار شده؛ موتور هوش مصنوعی و زمان‌بند هنوز متصل نیستند.
